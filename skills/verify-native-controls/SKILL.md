---
name: verify-native-controls
description: Verify native app or hardware controls when accepted commands, focus changes, recreated controls, or queued inputs may hide a failed effect.
---

Resolve the actual app, window, device, session, and installed build. Inspect supported capabilities through available documented APIs or UI tools before choosing a control path. A writable property or accepted command does not establish that the app applies it.

Bind each action to the current target and observe its resulting state through an independent read or visible effect. Refresh stale control identities after navigation or recreation. For audio or physical effects, distinguish software state from an effect that requires listening or physical observation; report the unavailable boundary accurately.

For queued or continuous input, carry target/session identity and cancel superseded work. Apply the product's intended latest-value or ordered-event semantics; do not collapse events that must all occur. Recheck target ownership after focus changes, reconnection, and asynchronous waits.

Exercise the reported trigger and relevant rapid-input or focus transition on the exact candidate/installed artifact. Record latency from input to observed effect when responsiveness is part of the requirement; unit regression counts do not establish native acceptance.

Keep tests within existing authorization and use reversible changes when possible. Restore only test changes whose target and current value are still owned by this operation; do not overwrite subsequent user input. Do not manufacture a success when a device, permission, or physical observation is unavailable. Continue all useful software-side checks and identify the remaining acceptance boundary.
